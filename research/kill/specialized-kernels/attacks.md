# Attacks

The issue asked for the strongest case for specialized kernels and the strongest case against them. These are adversarial cards, not a product recommendation.

## Strongest case for specialized kernels

### A-FOR-01. The invariant dies in the gap between app and store

**Kind.** attack  
**Decision.** supported as a physical risk. rejected as a reason to mint a semantic primitive.

If debit equals credit is only a Function the application remembers to call, a second writer, a partial retry, or a SQL UPDATE can unbalance the books. TigerBeetle's whole product is that argument. ERPNext had to write an immutable-ledger mode because ordinary row edits were the failure mode. PAF-ECF requisito I exists because a management system that holds a second set of numbers is a crime, not a refactor.

A generic interpreter that evaluates `DebitTotal == CreditTotal` after the write is late. The store has to refuse the write.

That is a specialized *evaluator and store*. It still evaluates a law the ontology already knows.

**Falsifier.** A production ledger that keeps statutory balance using only an after-the-fact Constraint, with concurrent posters, and never posts an unbalanced journal.

### A-FOR-02. Ordered valuation replay is not a fold over a bag

**Kind.** attack  
**Decision.** supported as runtime pressure

IAS 2 FIFO is an order. Moving average is a running state. Backdating a receipt changes later COGS. ERPNext says that recomputation is expensive and builds a sequenced job. A generic Function that sums `qty * rate` without layer identity will pass a unit test and fail a recall or a late supplier invoice.

If the only way to get the right number is a layer walker with pinned valid time, that walker is a specialized engine. The formula it walks remains an ontology Function.

**Falsifier.** A first vertical where unordered constraint eval produces the same statutory valuation as FIFO layers after backdated receipts, without a hidden order.

### A-FOR-03. Search is not arithmetic

**Kind.** attack  
**Decision.** supported for the class split

MRP explosion is a walk of a recipe. APS is combinatorial search. Wikipedia states the factorial blow-up. Palantir already admits several compute engines under one action.

If OS pretends a finite schedule is just another Function body, authors will write a greedy loop, call it deterministic, and ship infeasible work orders. The solver has to be allowed as a physical engine. The chosen plan still has to come back as Facts that an Action can refuse.

**Falsifier.** A plant where every feasible finite schedule is a closed-form Function of BOM and lead time, with no contention.

### A-FOR-04. The government already shipped the other engine

**Kind.** attack  
**Decision.** supported for fiscal and payroll filing

SEFAZ authorizes NF-e. Receita ships PVA. eSocial publishes S-1200. PAF-ECF certifies the POS and the back office together. Those programs are not optional caches. A filing that the official validator rejects is not a filing.

If "one executable ontology" means OS is the last checker, the thesis loses in Brazil on day one. The last checker is often the state.

**Falsifier.** A jurisdiction OS must support where the operational system is the unique legal validator and no external authorizer or PVA exists.

### A-FOR-05. Maintainability of tax and payroll tables

**Kind.** attack  
**Decision.** hypothesis

INSS, IRRF, FGTS, IBS, CBS, and ICMS change by statute and by period. A generic Function soup that inlines every table will rot. Commercial tax engines exist because the table maintenance is the product.

That can still be a versioned Function pack in the ontology, compiled by a physical emitter. The attack succeeds only if authors cannot keep the rules in the model and are forced to hide them in an opaque kernel.

**Falsifier.** A dated, testable Function library that tracks published tables without a sealed vendor kernel, across two tax families.

## Strongest case against specialized kernels

### A-AGAINST-01. A kernel below the ontology is a second chart of accounts

**Kind.** attack  
**Decision.** supported

H2 died for this reason. If the engine owns posting, the ontology's Journal is a view. Agents then improvise against the view while the kernel posts something else. Constitution §12 and PAF requisito I both forbid two books.

ERPNext and Odoo already implement accounting, stock, and MRP in one application runtime. They did not need a second language. They needed named documents, refuse-closed balance, and specialized jobs.

**Falsifier.** A mature system whose statutory truth lives only in a sealed kernel and whose ontology or document layer is allowed to disagree.

### A-AGAINST-02. The hard laws are already Functions, Constraints, and Actions

**Kind.** attack  
**Decision.** supported on present sibling evidence

Debit equals credit is a Constraint. Draft does not hit the books is a Constraint. Reverse is an Action. Explosion is a Function. Netting is a Function. Tax amount is a dated Function. Authorization is an Action with an external Effect. Money is a value type.

Sibling issues 18, 21, 24, 30, and 62 wrote those laws without asking for a kernel primitive. Issue 56 even tries to shrink Constraint and Policy to Bind. Adding AccountingKernel after that is aesthetic.

**Falsifier.** A required invariant that cannot be stated as a Function, Constraint, Action, or Bind without a hidden convention, in two independent corpora.

### A-AGAINST-03. Coupling kernels erase supported splits

**Kind.** attack  
**Decision.** supported

An InventoryAccountingKernel that always writes GL on movement contradicts L11. A FiscalInvoiceKernel that treats DANFE as the document contradicts CL-003. An MRPKernel that treats a material-feasible plan as executable contradicts L-06. A ProductKernel that unifies offer, specification, and valuation class contradicts issue 55.

The specialized kernel is how false cognates get concrete.

**Falsifier.** Independent perpetual systems that all post the same accounts on the same operational Event, including Odoo 19, ERPNext, and Moqui. That is also L11's falsifier.

### A-AGAINST-04. Certification is an Effect, not a nature

**Kind.** attack  
**Decision.** supported

Qualified signature, SEFAZ protocol, PVA acceptance, and eSocial receipt are observations about an external authority. Constitution §8 and §9 already require Action versus Event and unknown outcomes.

If those become kernel natures, every new country mints a new engine. The thesis wanted country rules in the model.

**Falsifier.** A first-party rule that local signature without an authorizer creates the NF-e in the ordinary path, including contingency.

### A-AGAINST-05. Performance arguments prove materialization, not a second meaning

**Kind.** attack  
**Decision.** supported

ValueFlows already says derive-from-events can be slow, so store the quantity. Constitution §6 already allows caches and materialized views. ERPNext's repost job is a materialization refresh. Palantir's Engine is a materializer.

None of those pages say the cache owns the law. A specialized physical engine that cannot quote the Function revision it evaluated is the failure mode H2 warned about.

**Falsifier.** A required business meaning that exists only in the evaluator and cannot be written as an ontology Function or Constraint.

## Reading the pair

The for-cards win on physics, certification, and search. The against-cards win on meaning.

That is why the folder rejects semantic kernels and supports physical evaluators. See `boundary.md`.
