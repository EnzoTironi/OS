# Counterexamples

**Status.** What would change the replace-OS answer.  
**Kind.** counterexample.  
**Decision.** `undetermined` until someone runs them. The folder verdict is `rejected` against current evidence, not against these possible futures.

Each card is a test a later agent can run. A pass on one card revises one law or one scorecard cell. It does not silently flip the folder verdict.

## X-001. Palantir keeps competing claims

**Attacks.** L-002, Palantir P1 cell.

Build V-001 in a Foundry tenant without merging ERP, WMS, spreadsheet, and chat into one property. Official docs then call that a System Silo and tell you to stop. If a later official page retracts E-002 and shows operators acting on multiple live claims with provenance-weighted policy, upgrade P1.

**Would flip replace-OS?** Only together with X-002, X-003, and X-004.

## X-002. Palantir or Open Foundry grow a hashed propose-revalidate path

**Attacks.** L-003, Palantir and Open Foundry P6 cells.

A durable proposal object, argument digest, and live re-check at commit, in product docs or opened code, not as a Workshop app.

AIP Manual confirm does not count. E-008.

## X-003. A writeback protocol that cannot split

**Attacks.** L-004, L-005, Palantir P8, Open Foundry P8.

Documented behavior where the external accept and the ontology commit either both land or both remain `unknown`, with no "external succeeded, ontology failed" sentence left on the page. E-006 currently has that sentence.

## X-004. Native known-then query

**Attacks.** L-007, Palantir P10, ERPNext P10, Ontologiq P10.

An engine API that answers S-007's two questions without a modeler-built amendment graph. Time series properties and "show cancelled entries" do not count unless they separate valid time from knowledge time.

## X-005. Ontologiq owns writes and history and still keeps unknown

**Attacks.** the "sidecar, not a core" reading in `distortions.md`.

If Ontologiq adds a fact or event store, multi-source claims, and transactional local writes without dropping `unknown` and hashed revalidation, it becomes a real replace-OS candidate. Alpha status and single-maintainer risk would remain operational, not semantic.

## X-006. ObjectStack carries caller authority through the body

**Attacks.** L-006.

If script actions execute every internal read and write as the caller, and `isSystem` cannot skip provenance, P12 becomes a pass. P8 and P10 would still be open.

## X-007. Moqui or ERPNext grow the protocol without the document god-object

**Attacks.** L-001 as applied to ERPs.

A service or DocType engine that refuses implicit CRUD, keeps requested/committed/planned/actual as different natures, and records unknown effects. GPL or implicit `update#Entity` would still block MIT-core reuse. Semantic kill would be real. License kill would remain. E-023.

## X-008. A new public platform this session did not open

**Attacks.** E-022.

S10 listed `cloudbadal007/foundry-ontology-open`, `ekyx/OpenFoundry`, GATE, and Open Ontology as unopened. A later worker may find a core that already enforces P1+P6+P8+P10. Until that tree is opened, "no existing platform" is a statement about the inspected set.

## X-009. The vertical is the wrong kill

**Attacks.** `vertical.md` as `hypothesis`.

If a real company can operate without first-class observations, stale revalidation, unknown effects, or known-then queries, V-001 is too hard and this kill test overfits the thesis. Constitution §9 and §13 currently say those cases are in scope. A domain note that shows they are rare and safely collapsed would weaken the folder, not by itself recommend Palantir.

## X-010. Hosted Palantir is "good enough" as a product, not as a core

**Attacks.** nothing in the metamodel. Attacks only a product-strategy reading of issue 68.

A company could buy Foundry, accept E-002 and E-006, and ship. That does not satisfy the thesis. It satisfies a different question. Record it as a product option, not as a killed core. Open question 21's criterion is semantic, not procurement.
